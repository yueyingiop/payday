PAYDAY SKILL SYSTEM / DESIGN NOTE

技能效果系统设计草案

目标是把表格中的技能效果整理成一套可复用、可测试、可由 KubeJS 扩展的声明式系统。这里先确定领域模型、运行时边界和脚本接口，暂时不编写具体技能效果 Java 代码。

本页面是设计讨论稿：示例 API、字段名和执行语义都属于草案，确认后再进入实现。

目标与边界

先稳定“技能是什么、何时生效、如何撤销、脚本如何扩展”这四件事。

希望得到的能力

  • 一份技能定义可以同时服务 GUI、存档、运行时和脚本。
  • 基础级与精通级只是同一技能的两个阶段，不复制整套逻辑。
  • 被动、条件被动、事件触发、资源操作和临时状态使用统一管线。
  • 技能重置、遗忘、玩家死亡或重载后，可以可靠地卸载旧效果。

暂时不做的事情

  • 不在本稿中决定每个技能的最终 Java 类实现。
  • 不把所有效果硬编码成 GUI 点击事件。
  • 不允许 KJS 直接写内部 NBT 或依赖私有运行时对象。
  • 不把客户端显示状态当作服务端技能状态。

核心原则

数据声明 服务端权威 可撤销 可测试 可脚本化 可观测

技能效果不应散落在 GUI、事件监听器、武器类和玩家 NBT 中；它们应由统一的运行时按来源管理。

核心模型

技能定义描述“有什么”，运行时状态描述“谁拥有、当前是什么阶段”。

SkillDefinition：稳定的技能身份

技能的身份和展示信息应稳定，不能因为 GUI 排列、语言变化或脚本加载顺序而改变。建议用完整 ID 作为唯一键，例如 payday:mastermind/medical/field_medic。

SkillDefinition {
  id: "payday:mastermind/medical/field_medic"
  category: "mastermind"
  series: "medical"
  tier: 3
  displayName: "Component.translatable(...)"
  baseCost: 3
  masteryCost: 6
  base: EffectSpec[]
  mastery: EffectSpec[]
  prerequisites: ConditionSpec[]
}

EffectSpec：效果的声明

效果只描述意图和参数，不保存玩家当前值。执行时由统一的处理器把它转换成属性修饰、事件监听、资源变化或临时状态。

EffectSpec {
  type: "attribute_modifier"
  target: "self"
  attribute: "movement_speed"
  operation: "multiply_total"
  value: 0.28
  when: ConditionSpec[]
  duration: "10s"
  cooldown: "30s"
  stacking: "replace_by_source"
}

ConditionSpec：统一条件表达式

“附近有敌人”“有变节敌人”“生命值低于 30%”“正在冲刺”都应成为可复用条件，而不是散落在各个技能处理器中的特殊判断。

player_state weapon_tag health_ratio armor_ratio exposure nearby_entities hostage_count converted_enemy movement equipment

SkillRuntime：玩家身上的运行时

它只属于服务端玩家，保存技能等级、已注册效果的来源句柄、冷却、充能和临时状态。GUI 获取的是同步后的只读快照。

  • activate：学习基础级或精通级后安装对应效果。
  • deactivate：遗忘时按 sourceId 卸载，而不是猜测要减多少。
  • rebuild：登录、重载、版本迁移后从技能等级重建全部效果。
  • sync：只同步 GUI 必需的等级、点数和临时提示。

现有 PhoneUpgrade 架构映射

技能系统应复用现有动作模型的优点，同时把物品升级的身份、技能阶段和运行时状态分开。

PhoneUpgradeAction

它是当前项目最接近“效果计划”的对象：不可变、可组合，并在应用时处理属性修饰、药水效果、Curios tick、护甲槽修改、事件代理、伤害规则、弹匣扩容和按键激活。

attributeeffectcurioTickaddProxyEventimmuneammoExpansionbindKeyActivate

PhoneUpgradeConfig

它承担内置效果注册表的角色：basic(series, level) 负责基础系列工厂，静态字段负责复杂特殊效果。技能系统可以保留这种“通用工厂 + 明确命名定义”的组织方式。

基础工厂特殊定义稳定 ID集中校验

PhoneUpgradeBuilder / KJS

KJS Builder 已经把动作能力映射为脚本链式 API。技能 API 应复用这些动作名，而不是另造一套互不兼容的属性、事件和概率命名。

categoryserieslevelprerequisiteeffectKeyaction

与 PhoneUpgradeBuilder 对齐的 KJS 形状

下面的 API 仍是草案，但方法名尽量沿用现有 PhoneUpgradeBuilder 和 PhoneUpgradeAction.Builder。这样现有手机升级脚本和未来技能脚本可以共享属性、药水效果、事件代理、概率免疫、弹匣扩容和按键激活的概念。

// 建议的技能 Builder：skill.stage(...).action(...) 内部复用 PhoneUpgradeAction.Builder
skills.register("payday:skill/mastermind/medical/1", skill => {
  skill.category("mastermind").series("medical").tier(1)
  skill.displayName("skill.payday.mastermind.medical.1")
  skill.base(stage => stage.cost(1).action(action => action
    .addProxyEvent("payday:medical_bag_thrown", event => {
      event.when("owner_is_player").then("apply_damage_reduction", { value: 0.15, duration: "5s" })
    })
  ))
})

建议的兼容层

技能系统对象参考现有对象职责
SkillDefinitionPhoneUpgradeItem 的系列、等级、前置元数据保存稳定技能 ID、Component 名称、阶级、基础/精通成本和阶段定义；不直接保存玩家当前等级。
SkillStageDefinitionPhoneUpgradeConfig 中一个静态 PhoneUpgradeAction描述某一阶段的效果计划，能够编译为一个或多个 PhoneUpgradeAction 或新的 EffectBinding。
SkillEffectCompilerPhoneUpgradeAction.Builder把 EffectSpec 编译成现有的 attribute/effect/curioTick/addProxyEvent 等动作；复杂效果落到专用处理器。
SkillRuntimePhoneItem.installedActions + 服务端事件分发根据玩家已学习的阶段安装、卸载和重建效果；每个效果绑定 skillId、stage 和 effectIndex。
SkillKjsBuilderPhoneUpgradeBuilder暴露相同的动作 Builder 能力，并额外提供技能阶段、条件、触发器、前置关系和生命周期事件。
 
// 伪代码：把声明式阶段编译为现有 PhoneUpgradeAction 能力
PhoneUpgradeAction action = SkillEffectCompiler.compile(stage,
    PhoneUpgradeAction.builder()
        .attribute(...)
        .effect(...)
        .addProxyEvent(...)
        .build());

runtime.bind(sourceId, action);
runtime.unbind(sourceId); // 按来源回收，而不是反向猜测数值

与当前代码的边界

PhoneUpgradeAction 目前适合“装备即生效”的手机升级。技能系统还需要学习等级、阶段依赖、临时状态、条件重算和 KJS 注册生命周期。因此建议保留 PhoneUpgradeAction 作为底层动作适配器，而不是让它直接承担技能点、GUI 同步或玩家技能等级存档。

运行时流程

所有入口最终汇聚到同一条效果管线，避免 KJS 和原生技能走两套规则。

01 · 事件或状态变化

Trigger

击杀、爆头、投掷医疗包、受到伤害、换弹、按键或定时 tick。

02 · 查找技能

Runtime

从玩家已激活技能索引中取得相关 EffectBinding。

03 · 判断条件

Condition

用统一上下文判断自身、武器、目标、范围和资源状态。

04 · 调度执行

Dispatcher

处理冷却、概率、优先级、叠加策略和效果来源。

05 · 改变世界

Action

修改属性、资源、状态、目标或生成可撤销的临时实例。

事件上下文应该包含什么

  • actor：拥有技能的玩家。
  • target：受到影响的实体，可为空。
  • item / weapon：触发事件时使用的物品。
  • position / level：范围判断和世界操作所需信息。
  • cause：伤害类型、击杀来源、事件来源。
  • transaction：本次事件中可撤销、可记录的变化集合。

事件与主动调用的边界

事件适合“发生了某件事后自动反应”，主动调用适合“玩家明确使用某个能力”。两者都通过 Dispatcher 进入，以便统一检查技能等级、冷却和权限。

// 伪代码：不是当前项目的实现代码
dispatcher.dispatch("entity_killed", context)
dispatcher.invoke("payday:medical/medic_bag", actor, args)

效果分类

按表格中的效果描述归纳，先建立少量稳定原语，再由它们组合复杂技能。

被动数值修改

稳定性、精准度、装填速度、移动速度、伤害、伤害减免、容量、护甲和生命值。

attribute_modifiercapacity_modifierdamage_modifier

条件被动

只有满足上下文条件才提供修改，例如附近敌人数量、低生命、暴露值、静止、冲刺、开镜。

conditional_modifiercondition_group

事件触发

投掷医疗包、爆头、击杀、呼喊、受到伤害、即将死亡、换弹、使用物品后执行动作。

event_listenerprobabilitycooldown

资源操作

恢复生命、护甲、护盾，补充弹药，消耗医疗包，改变技能点或经验。

resource_deltaresource_transfer

临时状态

持续时间、冷却、触发次数、充能、不可叠加或按来源替换，应该由状态实例统一管理。

temporary_statuschargesduration

目标与范围

自身、队友、附近敌人、人质、变节敌人和指定武器；范围选择器应独立于具体动作。

selfallynearbyhostage

特殊效果

不死图腾、伤害类型转换、武器模式限制、装备替换或自动使用物品等，不要强行伪装成普通属性。

special_actionguarded_trigger

组合效果

一个技能阶段可以有多个 EffectSpec；复杂效果由条件、目标选择、动作和冷却组合，不复制一份新类。

sequenceparallelfallback

技能效果不是 GUI 逻辑

GUI 只负责选择技能、显示状态和发送请求。真正的学习校验、资源扣除、效果激活与撤销必须在服务端完成。

server_authorityclient_snapshot

KJS 扩展设计

脚本使用稳定的公共入口；内部实现可以替换，脚本不应依赖私有类和内部存储。

建议提供的公共能力

  • 注册技能：添加新技能、阶段、成本、前置条件和翻译键。
  • 修改技能：在已有基础级或精通级上追加、替换或移除效果。
  • 注册条件：为脚本提供可组合的条件节点或命名条件。
  • 注册触发器：监听稳定的领域事件，而不是 Minecraft 内部事件细节。
  • 注册处理器：为新 EffectSpec 类型提供参数校验和执行逻辑。
  • 监听技能生命周期：激活、升级、遗忘、单树重置、全树重置。

伪代码：脚本侧定义技能

// 设计草案，不是当前可执行 KJS API
skills.register("payday:technician/repair/field_repair", skill => {
  skill.displayName = "skill.payday.technician.repair.field_repair"
  skill.tier = 2
  skill.base.cost = 2
  skill.base.effect("attribute_modifier", {
    target: "self", attribute: "repair_speed", value: 0.25

  skill.mastery.effect("event_action", {
    trigger: "repair_completed", action: "restore_armor", amount: 10
  })

KJS 边界建议

允许脚本做什么不建议脚本做什么理由
声明效果参数、条件、触发器和叠加策略直接修改玩家技能等级 NBT避免绕过前置条件、点数和同步逻辑。
注册自定义处理器并接收只读上下文持有内部实体处理器或事件总线对象防止脚本绑定实现细节，方便升级。
调用公开的资源、状态和目标选择 API任意执行没有权限检查的命令统一安全策略、日志和服务端权限。
监听技能生命周期事件在事件回调中递归触发同一事件需要调度器识别来源并限制递归深度。

叠加、优先级与安全

这些规则越早确定，后续新增技能和 KJS 扩展越不容易出现互相覆盖的问题。

每个效果都要有来源 ID

推荐来源格式：skillId + stage + effectIndex。属性修改、临时状态和事件监听都绑定来源，遗忘时按来源回收。

sourceId = "payday:mastermind/medical/field_medic#base/0"

叠加策略至少分五类

stackreplacemaxminrefresh_duration

例如同源临时减伤可以刷新持续时间；不同来源的移动速度可以相加，但应设置上限；同一特殊状态通常按优先级保留一个。

数值与时间统一规范

  • 百分比用明确的比例数值保存，不把“28%”作为自由文本解析。
  • 时间使用 tick 或带单位的 Duration 类型，展示文本另行翻译。
  • 乘法、加法、最终值修改必须明确 operation。
  • 所有效果参数在注册时校验，错误脚本应给出带技能 ID 的日志。

安全与性能

  • 技能效果只在服务端判定和执行，客户端不能自行发放资源。
  • 高频事件先做候选技能索引，再执行条件，避免遍历所有技能。
  • 范围查询、附近实体扫描和复杂条件要有缓存或节流。
  • KJS 处理器应限制执行时间、递归深度和每 tick 调用数量。

生命周期与重建

可重建比“在线修改很多状态”更重要：运行时应能从最小持久化数据恢复。

登录 / 加载

读取玩家技能等级和技能点，校验定义版本，构建 SkillRuntime，再同步 GUI 快照。

学习 / 精通

服务端验证点数和前置条件，更新等级，安装新增阶段的效果，广播状态变化。

遗忘 / 重置

先按来源卸载效果，再回收技能点；如果高阶条件失效，按依赖顺序递归遗忘。

死亡 / 复活

永久被动通常保留；临时状态按设计清理或保留，必须由效果类型声明，而不是统一猜测。

脚本重载

冻结新事件注册，卸载脚本来源，重新注册定义和处理器，再从玩家技能等级重建。

版本迁移

技能 ID 和效果参数应支持迁移表；不能依赖列表序号，否则新增技能会破坏旧存档。

建议落地顺序

先实现最小闭环，再逐步覆盖表格中的复杂效果。

阶段先解决什么验收标准
1. 身份与数据稳定技能 ID、阶段、成本、翻译键、前置条件和持久化格式。GUI、存档和脚本都不依赖列表序号。
2. 运行时骨架SkillRuntime、EffectBinding、来源 ID、activate/deactivate/rebuild。学习、遗忘、单树重置和全树重置都能无残留回收。
3. 基础原语属性修改、资源变化、持续状态、冷却、概率、目标选择。能覆盖表格中最常见的被动和事件效果。
4. 领域事件击杀、爆头、受伤、换弹、投掷物品、呼喊、濒死等统一事件。效果处理器不直接耦合 GUI 或具体武器实现。
5. KJS 公共层注册、修改、监听、校验、错误报告和来源隔离。脚本可以新增一个技能而不用重新编译核心模组。
6. 复杂效果不死图腾、伤害类型转换、模式限制、自动使用物品等特殊处理器。复杂效果仍能被测试、撤销并显示来源。

待确认问题

这些问题会直接影响 EffectSpec 和 KJS API，建议在开始写实现前定下来。

问题推荐的初始选择需要确认的原因
技能 ID 是否永远独立于中文名称？是，ID 只允许稳定的英文路径。翻译和改名不会破坏存档、KJS 和迁移。
基础级与精通级如何叠加？精通包含基础级；激活精通时保留基础效果并追加精通效果。表格描述通常是“基础效果 + 精通额外效果”，需要明确是否存在覆盖例外。
同类百分比修改如何叠加？默认按 operation 和来源分别计算，特殊效果显式声明上限或替换。避免不同技能互相覆盖、遗忘后数值无法恢复。
KJS 是否允许注册全新 EffectSpec 类型？允许，但必须注册参数 schema、处理器和权限/性能限制。这是可复用性和稳定性之间的主要边界。
复杂效果是否需要事务回滚？资源和属性操作需要；外部副作用必须记录来源并提供补偿动作。事件中途失败时，避免只扣资源但没有施加效果。
客户端是否展示脚本自定义文本？通过翻译键和结构化参数同步，不同步任意富文本脚本。保证可翻译、可控长度且不让客户端执行脚本内容。

本稿只记录设计方向。下一步应先确认“效果原语、事件上下文、叠加策略、KJS 边界”四项，再开始实现最小运行时闭环。
